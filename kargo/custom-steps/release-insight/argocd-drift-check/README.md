# argocd-drift-check

Before promoting, checks that the target Argo CD Application is still what git says it is. It blocks the promotion
when live resources have drifted from git (someone edited prod by hand) or the app is unhealthy, so a promotion never
silently overwrites, or builds on top of, an unknown state.

The built-in `argocd-update` and `argocd-wait` steps handle syncing and waiting *after* the change; this step is the
check *before* it.

## Prerequisites

Beyond the [common prerequisites](../../../../README.md#prerequisites):

| | |
|---|---|
| Cluster add-ons | **Argo CD**, managing the Application to check, and integrated with the Kargo agent that runs the `custom-steps` shard |
| Reachable services | The Kubernetes API of the Argo CD cluster (provided through the capability) |
| Accounts / credentials | None: Kargo provisions them |
| Kargo capabilities | **`access-argocd`** (declared by the step). Kargo provides credentials for the `kargo-promotion-argocd` ServiceAccount, which can read Applications |
| Network egress | None |
| Inputs | None |

The capability gives Kubernetes API access to `Application` objects, not access to the Argo CD API server, so the
step reads the Application's `status` rather than running `argocd app diff`.

## Config

| Key | Type | Required | Default | Description |
|---|---|---|---|---|
| `app` | string | yes | — | Argo CD Application name |
| `namespace` | string | no | `$ARGOCD_NAMESPACE`, else `argocd` | Namespace of the Application |
| `requireSynced` | bool | no | `true` | Block when the app or any of its resources is not `Synced` |
| `requireHealthy` | bool | no | `true` | Block when the app's health is not `Healthy` |
| `ignoreKinds` | list | no | `[]` | Resource kinds to leave out of the drift report, e.g. `[Job]` |
| `argocdURL` | string | no | — | Argo CD UI base URL, to link the app from the promotion |

## Outputs

| Key | Type | Description |
|---|---|---|
| `app`, `namespace` | string | The Application checked |
| `syncStatus`, `healthStatus` | string | From the Application's status |
| `revision` | string | Synced revision (comma-joined for multi-source apps) |
| `outOfSync` | list | `{group, kind, namespace, name, status, health}` for every resource that is not `Synced` |
| `drifted` | bool | Whether the step blocks for drift (`requireSynced` and something is out of sync) |
| `unhealthy` | bool | Whether the step blocks for health (`requireHealthy` and health is not `Healthy`) |
| `links` | list | Link to the app in the Argo CD UI, when `argocdURL` is set |

When the step blocks, the message names the resources, e.g.
`Promotion blocked: Application argocd/guestbook-prod is OutOfSync: 2 resource(s) differ from git: apps/Deployment/prod/guestbook (OutOfSync), batch/Job/prod/migrate (OutOfSync).`

## Example

```yaml
steps:
- uses: argocd-drift-check
  config:
    app: guestbook-${{ ctx.stage }}
    ignoreKinds: [Job]
    argocdURL: https://argocd.example.com
- uses: argocd-update
  config:
    apps:
    - name: guestbook-${{ ctx.stage }}
```

## Notes

- Read-only; retries are safe. `defaultErrorThreshold: 3` tolerates brief API errors.
- `ignoreKinds` only filters the resource list. If the app itself is `OutOfSync` and `requireSynced` is true, the
  promotion is still blocked; set `requireSynced: false` to check health only.
- Without the capability (or without an Argo CD integration on the agent) the step fails with
  `the step needs capabilities: [access-argocd]`.
- Tested: harness fixtures in [`test/fixtures/argocd-drift-check`](../../../../test/fixtures/argocd-drift-check), using
  canned Application objects (`DRIFT_CHECK_APP_FILE`, a test-only hook) and fake in-cluster credentials.
  **Untested against a live Argo CD** so far.
