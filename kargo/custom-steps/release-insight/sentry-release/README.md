# sentry-release

Records a promotion in [Sentry](https://sentry.io): creates the release, optionally links its commits, and records a
deploy to the Stage's environment. Sentry then shows which release each environment runs, deploy markers on its graphs,
and (with commits linked) suspect commits for new issues. Rollbacks are recorded like any other promotion.

It isn't a gate: it fails only when Sentry can't record the release or deploy, for example a wrong token or project.

## Prerequisites

Beyond the [common prerequisites](../../../../README.md#prerequisites):

| | |
|---|---|
| Cluster add-ons | None |
| Reachable services | Sentry (`sentry.io`, or your self-hosted Sentry's URL) |
| Accounts / credentials | A Sentry auth token with `project:releases` (an organization auth token works), in a Kargo secret. To link commits, the repository connected in Sentry (**Settings → Integrations**, e.g. GitHub) |
| Kargo capabilities | None |
| Network egress | Sentry, over HTTPS |
| Inputs | None. The app should report the same release name to Sentry through its SDK (e.g. `release="app@1.5.0"`), so its events belong to the releases this step records |

## Config

| Key | Type | Required | Default | Description |
|---|---|---|---|---|
| `authToken` | string | yes | — | Sentry auth token with `project:releases`. Pass it from a Kargo secret |
| `org` | string | yes | — | Sentry organization slug |
| `project` | string | yes | — | Sentry project slug |
| `version` | string | yes | — | Release version, matching the release the app's SDK reports, e.g. `app@1.5.0` |
| `environment` | string | no | the Stage name | Environment the deploy is recorded to |
| `repo` | string | no | — | Repository name as connected in Sentry, e.g. `acme/app`. With `to`, links the release's commits |
| `from` | string | no | — | Commit the Stage ran before (the start of the commit range). Without it, Sentry picks the range itself |
| `to` | string | with `repo` | — | Commit the Stage runs now |
| `finalize` | bool | no | `true` | Mark the release as released |
| `url` | string | no | `https://sentry.io` | Sentry URL, for self-hosted Sentry |

The deploy is named after the promotion, so a retried promotion replaces its deploy instead of adding a second one.

## Outputs

| Key | Type | Description |
|---|---|---|
| `version` | string | The release |
| `environment` | string | The environment the deploy was recorded to |
| `created` | bool | Whether this promotion created the release (false when it already existed, e.g. from an earlier Stage) |
| `commits` | number | Commits linked to the release |
| `deployId` | string | Sentry's id for the deploy |
| `links` | list | The release's page in Sentry, shown as a link on the step |
| `error` | string | Why the step failed, e.g. a rejected token or an unknown project; empty on success |

## Example

Record each promotion after the deploy, with the commits since what the Stage ran before (stored on the Stage with
`set-metadata`, as the [`release-diff`](../release-diff/README.md) demo does). `continueOnError` keeps a Sentry
problem from failing a promotion that has already deployed:

```yaml
steps:
# ... the steps that deploy the new Freight ...
- uses: sentry-release
  as: sentry
  continueOnError: true
  config:
    authToken: ${{ secret('sentry').token }}
    org: acme
    project: app
    version: app@${{ imageFrom("ghcr.io/acme/app").Tag }}
    repo: acme/app
    from: ${{ quote(stageMetadata(ctx.stage)?.lastCommit ?? "") }}
    to: ${{ quote(commitFrom("https://github.com/acme/app").ID) }}
- uses: set-metadata
  config:
    updates:
    - kind: Stage
      name: ${{ ctx.stage }}
      values:
        lastCommit: ${{ quote(commitFrom("https://github.com/acme/app").ID) }}
```

## Try it

Demo project `custom-steps-release-insight` ([kargo/projects/release-insight](../../../projects/release-insight)). Both
Stages need the `sentry` secret described in [secrets/README.md](../../../../secrets/README.md#sentry-the-release-insight-group).

| Stage | Expected |
|---|---|
| `sentry-release-pass` | Promotion succeeds. The step's output has `created: true` and a link to release `guestbook@<tag>` in Sentry, which lists a deploy to `sentry-release-pass`. Promoting another Freight records another release |
| `sentry-release-blocked` | Promotion fails. The step uses a Sentry project that doesn't exist, and its `error` output names it |

## Notes

- Calls the Sentry API directly (create the release, link commits, finalize, record the deploy) with `curl`; the token
  is sent in a header and never printed.
- Creating a release that already exists is fine, so promoting the same Freight to the next Stage only adds a deploy.
- A retried promotion replaces its deploy (Sentry keeps one deploy per name and environment); its `deployId` changes.
- Run it after the steps that deploy, so the deploy marker means the version is running.
- Tested: harness fixtures in [`test/fixtures/sentry-release`](../../../../test/fixtures/sentry-release), against a fake
  Sentry API (`make test-services`). Checked by hand against sentry.io.
