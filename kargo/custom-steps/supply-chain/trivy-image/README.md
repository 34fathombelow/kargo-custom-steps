# trivy-image

Scans a container image for known vulnerabilities with [Trivy](https://trivy.dev) and blocks the promotion when it
finds any at the configured severities.

## Prerequisites

Beyond the [common prerequisites](../../../../README.md#prerequisites):

| | |
|---|---|
| Cluster add-ons | None |
| Reachable services | None |
| Accounts / credentials | Registry credentials only for private images (`username` / `password`) |
| Kargo capabilities | None |
| Network egress | The registry of the image being scanned. The vulnerability DB and the Java index DB are baked into the step image, so Trivy downloads nothing else |
| Inputs | If you use `ignorefile`: the file, checked out by an earlier `git-clone` step |

The step image is large (about 3.4 GB, mostly the two vulnerability DBs), so the first promotion on a node takes a
while to pull it.

## Image

`ghcr.io/34fathombelow/trivy:0.76.0`, built from [`docker/trivy/Dockerfile`](../../../../docker/trivy/Dockerfile) and published by this repo's
GitHub Actions:

```dockerfile
# Trivy with the vulnerability DB and the Java index DB pre-downloaded, so the
# trivy-image step does not download them on every promotion. The Java DB is required: Trivy aborts on any
# image containing Java artifacts when it is missing and updates are skipped.
# The DBs go stale: images.yaml rebuilds this image weekly.
# renovate: datasource=docker depName=aquasec/trivy
ARG TRIVY_VERSION=0.76.0

FROM aquasec/trivy:${TRIVY_VERSION}
LABEL org.opencontainers.image.source=https://github.com/34fathombelow/kargo-custom-steps \
      org.opencontainers.image.description="Trivy with a pre-baked vulnerability DB for the Kargo trivy-image custom step"
ENV TRIVY_CACHE_DIR=/opt/trivy-cache \
    TRIVY_SKIP_DB_UPDATE=true \
    TRIVY_SKIP_JAVA_DB_UPDATE=true \
    TRIVY_NO_PROGRESS=true \
    TRIVY_DISABLE_TELEMETRY=true \
    HOME=/tmp
RUN apk add --no-cache bash jq && \
    mkdir -p /opt/trivy-cache && \
    TRIVY_SKIP_DB_UPDATE=false trivy image --download-db-only && \
    TRIVY_SKIP_JAVA_DB_UPDATE=false trivy image --download-java-db-only && \
    chown -R 65532:65532 /opt/trivy-cache && chmod -R a+rwX /opt/trivy-cache
USER 65532:65532
```

## Config

| Key | Type | Required | Default | Description |
|---|---|---|---|---|
| `image` | string | yes | — | Image to scan. Prefer a digest reference from Freight: `${{ imageFrom(repo).RepoURL + "@" + imageFrom(repo).Digest }}` |
| `severity` | string | no | `CRITICAL` | Comma-separated severities that block: `UNKNOWN`, `LOW`, `MEDIUM`, `HIGH`, `CRITICAL` |
| `ignoreUnfixed` | bool | no | `true` | Ignore vulnerabilities that have no fixed version yet (you can't act on them) |
| `ignorefile` | string | no | — | Workdir-relative [`.trivyignore`](https://trivy.dev/latest/docs/configuration/filtering/#trivyignore) file listing accepted vulnerability IDs |
| `username`, `password` | string | no | — | Registry credentials, e.g. `${{ secret('registry').username }}` |

## Outputs

| Key | Type | Description |
|---|---|---|
| `blocked` | bool | Whether the promotion is blocked: vulnerabilities at the configured severities were found, or the scan could not run |
| `scanned` | bool | `false` when the scan could not run at all (e.g. the registry refused the pull); see `error` |
| `error` | string | Only when `scanned` is `false`: why |
| `image` | string | The image that was scanned |
| `total` | int | Number of distinct vulnerabilities found |
| `counts` | object | Count per severity, e.g. `{"CRITICAL": 3}` |
| `vulnerabilities` | list | The first 100: `{id, pkg, installed, fixed, severity, title}` |
| `truncated` | bool | Whether `vulnerabilities` was cut at 100 (the output limit is 256 KiB) |
| `dbUpdatedAt` | string | When the baked-in vulnerability DB was built, so you can see how fresh the scan was |
| `links` | list | Advisory links for the first 10 vulnerabilities, rendered as links in the Kargo UI |

When `blocked` is true the step **fails** and the promotion stops; the output still lists what blocked it.

## Example

```yaml
steps:
- uses: trivy-image
  as: scan
  config:
    image: ${{ imageFrom('ghcr.io/example/app').RepoURL + "@" + imageFrom('ghcr.io/example/app').Digest }}
    severity: HIGH,CRITICAL
```

|---|---|---|
| `trivy-pass` | `alpine:3.24.2` | Promotion succeeds; output `blocked: false` |

## Notes

- **The vulnerability DB goes stale.** It's baked in when the image is built. The image workflow rebuilds the image weekly
  and re-pushes the same `<version>` tag, but a node that already pulled that tag keeps its cached copy. Check
  `dbUpdatedAt` in the output; to force a fresh DB, point the step at the immutable `<version>-<date>-<sha>` tag of the
  latest build.
- Read-only, so retries are safe.
- Results can change over time for the same image as new vulnerabilities are published; that is the point of
  scanning at promotion time rather than only at build time.
- Tested: harness fixtures in [`test/fixtures/trivy-image`](../../../../test/fixtures/trivy-image), including an image with
  Java artifacts (which needs the baked-in Java DB).
