# flyway-migrate

Applies [Flyway](https://documentation.red-gate.com/flyway) SQL migrations to a Stage's database during promotion,
so the schema travels with the Freight instead of drifting on its own schedule. Safe to retry, and safe to roll back.

## Prerequisites

Beyond the [common prerequisites](../../../../README.md#prerequisites):

| | |
|---|---|
| Cluster add-ons | **A database the step's image has a driver for:** PostgreSQL, MySQL/MariaDB, SQL Server, Oracle, SQLite, H2, HSQLDB or Firebird. Snowflake, Databricks, Cassandra, Couchbase, MongoDB, SingleStore, BigQuery and Spanner are left out to keep the image small ([add one](../../../../docker/flyway/README.md#supported-databases)). The demo uses a Postgres that Argo CD deploys to cluster `custom-steps-agent`: [`prereqs/flyway-migrate`](../../../../prereqs/flyway-migrate)) |
| Reachable services | The database, **from the `custom-steps` agent cluster** where promotion pods run |
| Accounts / credentials | A database user that can create tables. The demo reads it from the `flyway-db` Secret: [`secrets/README.md`](../../../../secrets/README.md#flyway-db-the-data-group) |
| Kargo capabilities | None |
| Network egress | None beyond the database |
| Inputs | The migrations (`V<version>__<description>.sql`), checked out by an earlier `git-clone` step |

## Image

`ghcr.io/34fathombelow/flyway:13.10.3`, built from [`docker/flyway/Dockerfile`](../../../../docker/flyway/Dockerfile) and published by this repo's
GitHub Actions:

```dockerfile
# Flyway, pinned, plus jq (the flyway-migrate step shapes Flyway's JSON output
# and decodes its JSON-encoded config with it), set up to run as 65532.
#
# Slimmed down from the official alpine image: the final image starts from plain
# alpine and copies in Flyway's own Java runtime and /flyway, without the large
# drivers for Snowflake, Databricks, Cassandra, Couchbase, MongoDB, SingleStore
# and the AWS/GCP add-ons (deleting them in a later layer wouldn't shrink it).
# Kept: PostgreSQL, MySQL/MariaDB, SQL Server (+jTDS), Oracle, SQLite, H2,
# HSQLDB, Firebird. See README.md to add a driver.
# renovate: datasource=docker depName=flyway/flyway
ARG FLYWAY_VERSION=13.10.3
# Keep in step with the alpine release the Flyway image is built on.
# renovate: datasource=docker depName=alpine
ARG ALPINE_VERSION=3.24.2

FROM flyway/flyway:${FLYWAY_VERSION}-alpine AS flyway
# Each removed driver's Flyway plugin goes too: Flyway loads every plugin at
# startup, and a plugin without its driver crashes it (NoClassDefFoundError).
RUN cd /flyway/drivers && \
    rm -rf aws cassandra couchbase gcp mongo \
           databricks-jdbc-*.jar google-cloud-storage-*.jar singlestore-jdbc-*.jar snowflake-jdbc-*.jar && \
    cd /flyway/lib/flyway && \
    rm -f flyway-database-cassandra-*.jar flyway-database-nc-cassandra-*.jar flyway-database-nc-couchbase-*.jar \
          flyway-database-nc-mongodb-*.jar flyway-database-databricks-*.jar flyway-database-snowflake-*.jar \
          flyway-singlestore-*.jar flyway-gcp-bigquery-*.jar flyway-gcp-spanner-*.jar flyway-locations-s3-*.jar

FROM alpine:${ALPINE_VERSION}
LABEL org.opencontainers.image.source=https://github.com/34fathombelow/kargo-custom-steps \
      org.opencontainers.image.description="Flyway for the Kargo flyway-migrate custom step"
RUN apk add --no-cache bash ca-certificates jq
COPY --from=flyway /opt/java/openjdk /opt/java/openjdk
COPY --from=flyway /flyway /flyway
# Flyway writes nothing to $HOME, but the JVM does (hsperfdata, prefs).
ENV JAVA_HOME=/opt/java/openjdk \
    PATH=/flyway:/opt/java/openjdk/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin \
    HOME=/tmp JAVA_TOOL_OPTIONS="-XX:-UsePerfData -Djava.util.prefs.userRoot=/tmp"
USER 65532:65532
```

## Config

| Key | Type | Required | Default | Description |
|---|---|---|---|---|
| `url` | string | yes | — | JDBC URL, e.g. `jdbc:postgresql://host:5432/db` |
| `username` | string | yes | — | Database user |
| `password` | string | yes | — | Database password. Pass it with `${{ secret('<name>').password }}`, never inline |
| `migrationsPath` | string | yes | — | Workdir-relative directory holding the migrations |
| `target` | string | no | latest | Migrate up to this version only |
| `dryRun` | bool | no | `false` | Report pending migrations without changing anything (no repair, no migrate) |
| `baselineOnMigrate` | bool | no | `false` | Baseline a non-empty schema that has no Flyway history table yet |
| `connectRetries` | int | no | `3` | How many times to retry the connection before failing |

Every value reaches Flyway byte for byte: the fixtures include a password with quotes, a backslash and digits.

## Outputs

| Key | Type | Description |
|---|---|---|
| `schemaVersion` | string | Schema version after the step (`""` for an empty database) |
| `initialSchemaVersion` | string | Schema version before the step |
| `migrationsApplied` | int | Migrations applied by this promotion (0 on a re-run or rollback) |
| `applied` | list | `{version, description}` of each applied migration |
| `pending` | list | Dry run only: `{version, description}` of what would be applied |
| `rollback` | bool | The database is **ahead** of these migrations: older Freight was promoted |
| `futureVersions` | list | Versions applied to the database but missing from this Freight |
| `dryRun` | bool | Whether this was a dry run |

A later step reads them as `outputs['migrate'].schemaVersion` in a Stage's promotion template, or as
`task.outputs['migrate'].schemaVersion` inside the same PromotionTask.

## How it behaves

- **`flyway repair` runs first.** A failed non-transactional migration (e.g. `CREATE INDEX CONCURRENTLY`) leaves a
  failed row in `flyway_schema_history` that would block every later run. Repair clears it; on a healthy history it is a no-op.
- **Rollbacks are a clean no-op.** Missing and future migrations are ignored, so promoting older Freight (a manual
  rollback, or Kargo auto-rollback) succeeds without touching the schema and reports `rollback: true`. Flyway OSS never
  migrates down; write forward-compatible migrations (expand/contract) so older app versions still work on the newer schema.
- **Idempotent.** Applied versions are skipped, so Kargo step retries and re-promotions are safe.
- **Concurrent promotions serialize.** Flyway takes a database lock (an advisory lock on Postgres) while migrating.
- **Clear failures.** An empty password, an unreachable database, bad credentials or a missing migrations directory each fail
  with one line naming the cause, not a Java stack trace.

## Example

```yaml
steps:
- uses: git-clone
  config:
    repoURL: https://github.com/example/app.git
    checkout:
    - commit: ${{ commitFrom('https://github.com/example/app.git').ID }}
      path: ./src
- uses: flyway-migrate
  as: migrate
  config:
    url: ${{ secret('app-db').url }}
    username: ${{ secret('app-db').username }}
    password: ${{ secret('app-db').password }}
    migrationsPath: ./src/db/migrations
```

## Try it

Demo project `custom-steps-data` ([kargo/projects/data](../../../projects/data)). Argo CD deploys
the demo Postgres ([`prereqs/flyway-migrate`](../../../../prereqs/flyway-migrate)). Create the `flyway-db` secret in the
Kargo UI first ([`secrets/README.md`](../../../../secrets/README.md#flyway-db-the-data-group)).

| Stage | Do | Expected |
|---|---|---|
| `dev` | Promote the newest Freight | Succeeds; `migrationsApplied: 3`, `schemaVersion: "3"`. Promote again: `migrationsApplied: 0` |
| `rollback` | After `dev`, promote the same Freight here. This Stage applies the older migration set (`migrations-v1`, V1 only), standing in for an older release | Succeeds as a no-op; `rollback: true`, `futureVersions: ["2", "3"]` |

In real use, the rollback case happens when you promote older Freight whose migrations the database has already moved past.
